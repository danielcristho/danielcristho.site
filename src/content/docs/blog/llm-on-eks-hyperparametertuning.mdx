Hi there! 👋🏽 A quick recap before we start. In the [Kubeflow pipeline post](/blog/llm-on-eks-pipeline-kubeflow/), we fine-tuned `Qwen2.5-1.5B-Instruct` with LoRA, quantized the model with AWQ, and pushed the result to S3. In the [previous post](/blog/llm-on-eks-gitops/), vLLM started serving that model from S3 as `qwen-lora`, and switching to a new model became a Git commit that Argo CD rolls out with no downtime. Let's call the model that serves now model A.

The chatbot from the previous post is an assistant for AWS Community Day Jakarta 2026, where this series became a talk. The chatbot answers questions about the agenda, rooms and speakers from a small knowledge base built from the event page.

But the LoRA settings behind model A were a guess. So in this post, we will set up a way to measure those settings. The pipeline searches for better settings with Ray Tune, and when a config is better than the old one, we roll out the new model (model B). The full architecture is in the [previous post](/blog/llm-on-eks-gitops/#architecture).

## TL;DR

- Before tuning anything, we check if the event chatbot needs fine-tuning at all.
- A new `tune_hyperparams` step runs Ray Tune inside a single GPU pod. The step searches LoRA `r`, `lora_alpha` and `learning_rate` on a held-out eval split.
- ASHA stops weak trials after one epoch, so 6 trials cost a lot less than 6 full trainings.
- The hand-picked settings from the pipeline post run as one of the trials (the baseline), so we can see where that guess ranks.
- If the best config does not beat the baseline, the pipeline stops and the served model stays as it is.
- Each run writes its model to its own S3 prefix. Rolling the model out is the same Git commit as in the previous post.
- The pipeline has not run yet. What we measured so far: model A scores 6/15 with the whole knowledge base in the prompt, and 11/15 when the prompt gets the matching lines instead.

## Why Tune at All?

In the pipeline post, I picked the LoRA settings (`r=16`, `alpha=32`, `lr=5e-5`) because those are common defaults, not because I measured them. The pipeline trained on all 200 examples with no held-out set. The one signal we had was training loss, and the loss was going down when the epoch ended. That tells us the model was learning. It does not tell us the settings were good. Also, `5e-5` is on the low side for LoRA. Most setups use something between `1e-4` and `2e-4`.

So the problem is not that the first model is bad. We did not measure the first model. In this post, we hold out 20% of the data, try several LoRA configs under the same conditions, and keep the config with the lowest eval loss. The old defaults run as one of the trials. If the old defaults have the lowest loss, that is also a result: we know the settings are good.

## Does the Chatbot Need Fine-Tuning at All?

Tuning answers "which LoRA config is best?". But there is a question before that one: "does LoRA beat the base model at all?". If LoRA does not, we are tuning something we do not need.

For our event chatbot, my guess is no. People ask about facts: times, rooms, speakers. Facts go in the prompt, not in the weights. The whole event knowledge base (`src/knowledge_base.md`, generated from the event API by `src/build_kb.py`) is around 2k tokens. That fits in `max_model_len` 4096, so `Qwen2.5-1.5B-Instruct` can read the knowledge base from the system prompt without a retrieval index.

Fine-tuning changes how the model answers, not what the model knows. And an agenda baked into the weights goes stale once the schedule changes.

Eval loss is not chatbot quality either. A lower loss does not mean the model gets "what time is the LLM talk?" right.

### What Fine-Tuning Could Teach

The knowledge base goes into every request, so the training data has to look the same: context in the prompt, answer taken from the context. The goal is not to memorize the agenda. The goal is to teach the behavior around the agenda: find the answer in the context, and say "I don't know" when the answer is not there. A 1.5B model often gets the second part wrong and makes up a time or a speaker.

**The dataset, generated from `src/knowledge_base.md` with templates (no LLM in the loop):**

- Each session gives a few questions, in Indonesian and English: when is X, which room is X in, who presents X.
- The context of each example is a mini knowledge base: the line with the answer plus ~8 random lines around it. That keeps each example around 300 tokens instead of 2k, which matters on a T4.
- Unanswerable examples: the same question with the answer line removed from the context. The target reply is "not in the event info, check jakarta.awscommunity.id/comday". Plus questions the event page does not cover, like parking, wifi and dress code.
- The split is by session, not by row. Sessions in the test set do not show up in training, so the test score measures lookup, not memory.

**Scoring, automatic:**

- Answerable: correct if the reply contains the right time, room or name.
- Unanswerable: correct if the reply says it does not know and contains no invented time or name.

**Three models, one test set:**

| Model                                              | Question it answers              |
| -------------------------------------------------- | -------------------------------- |
| Base Qwen + knowledge base                         | The no-training baseline         |
| LoRA, old settings (`r=16`, `alpha=32`, `lr=5e-5`) | Does fine-tuning help?           |
| LoRA, Ray Tune's best config                       | Does tuning help on top of that? |

Ray Tune ranks trials with `eval_loss`, because eval loss is cheap per trial. The rollout decision uses test accuracy. And we run Ray Tune when the old-settings LoRA beats the base model. If the old-settings LoRA does not, that is the finding: for a chatbot about facts, a knowledge base in the prompt is enough, and fine-tuning or tuning adds nothing.

My guess: the base model can handle simple lookups like "what time is X?". If there is a gap, the gap shows up in "I don't know" answers and in multi-step questions like "what's on the Main Stage after lunch?".

**What has to change before this runs:**

- The dataset. `mlabonne/guanaco-llama2-1k` uses the Llama-2 `[INST]` template. The new dataset is built with Qwen's chat template.
- Loss masking. `finetune_lora` and `tune_hyperparams` set `labels = input_ids`, so the loss covers the prompt too. With a long context in the prompt, most of that loss is about copying the knowledge base. Prompt tokens need the label `-100`, so the loss counts the answer and nothing else.

## What Changed in the Pipeline

The pipeline grabs 200 examples, then Ray Tune tries 6 LoRA configs. One of the 6 is the old config from the pipeline post. The best config has to beat that old config. If the best config does not, the pipeline stops and model A stays. If the best config is better, we train with that config, shrink the model with AWQ, and push the result to S3.

The diagram shows the trials side by side, but on our single T4 the trials run one at a time. The last box, "Serve with vLLM", is the Git commit from the previous post. The pipeline itself stops at S3.

### Ray Tune in One Pod

We already have a RayCluster in the cluster, but that RayCluster is busy serving vLLM. Its GPU workers hold the model, and taking one worker away for training means one replica less for users. So `tune_hyperparams` starts its own Ray inside the pipeline pod, on the one T4 that the pod gets:

```python
ray.init(num_gpus=1 if use_gpu else 0, include_dashboard=False)
```

When the step ends, Ray goes away with the pod. There is no second RayCluster to run or pay for.

The search space covers three settings:

```python
param_space={
    "lora_r": tune.choice([8, 16, 32]),
    "lora_alpha": tune.choice([16, 32, 64]),
    "learning_rate": tune.loguniform(5e-5, 5e-4),
},
```

Each trial is a short LoRA training on 80% of the data, evaluated on the other 20% at the end of every epoch. The trial reports `eval_loss` to Ray Tune after each epoch, and ASHA works with that number. ASHA (`grace_period=1`, `reduction_factor=2`) compares trials after the first epoch and stops the weak ones, so weak trials do not use GPU time on epochs 2 and 3. A config that stays in the top half runs up to `max_t`, 3 epochs.

Two settings are there because of the single T4:

- `max_concurrent_trials=1`: one GPU, one trial at a time.
- `reuse_actors=False`: every trial gets a fresh worker process, so the GPU memory of the last trial is freed when the trial ends. We hit memory left behind in one process before, when merging Llama in the pipeline post.

### The Baseline Gate

The old settings (`r=16`, `alpha=32`, `lr=5e-5`) go in as the first trial:

```python
search_alg=BasicVariantGenerator(points_to_evaluate=[baseline]),
```

So the baseline runs under the same conditions as the other trials, and the trials table shows where the baseline ranks. The step returns the best config plus `beats_baseline`. The flag is false when the baseline itself has the lowest eval loss.

The pipeline uses that flag to decide whether to train at all:

```python
with dsl.If(search.outputs["beats_baseline"] == True):
    train = finetune_lora(..., lora_r=search.outputs["lora_r"], ...)
    quant = quantize_and_upload(model_in=train.outputs["model_out"], ...)
```

If the baseline has the lowest loss, model A was trained with the best config we found, and training again changes nothing. The pipeline skips the full training and AWQ, the two longest GPU steps, and model A stays.

## Rolling Out the New Model

When a config is better than the baseline, `quantize_and_upload` writes model B to `pipeline-output/<run-id>`. The pipeline stops there and has no access to the cluster. Rolling out model B is the commit from the [previous post](/blog/llm-on-eks-gitops/#rolling-out-model-b):

```bash
$ sed -i 's|^modelPrefix:.*|modelPrefix: pipeline-output/<run-id>|' manifests/vllm/values.yaml
$ git add manifests/vllm/values.yaml
$ git commit -m "feat(new model): serve <run-id>"
$ git push
```

Argo CD syncs the commit, KubeRay builds a new cluster with model B, and model A serves until model B is ready.

## Running the Pipeline

First, compile the pipeline. This writes `finetune_pipeline.yaml` next to `finetune_pipeline.py`:

```bash
$ just compile
```

Then open the KFP UI. There is no public load balancer for the UI, so we port-forward:

```bash
$ just kfp-ui   # KFP UI at localhost:8080
```

Upload `finetune_pipeline.yaml`, hit **Create run**, and set `bucket_name`. The other parameters have defaults:

| Parameter         | Default                      |
| ----------------- | ---------------------------- |
| `base_model`      | `Qwen/Qwen2.5-1.5B-Instruct` |
| `num_examples`    | 200                          |
| `num_trials`      | 6                            |
| `tune_max_epochs` | 3                            |
| `s3_prefix`       | `pipeline-output`            |

The trials table shows up as the `trials_report` artifact of the `tune-hyperparams` step.

To score a model on the knowledge base questions, port-forward vLLM and run the eval script. `--no-kb` leaves the knowledge base out of the system prompt:

```bash
$ just vllm-forward
$ just eval --label model-v1+kb
$ just eval --label model-v1-no-kb --no-kb
```

## What We Know So Far

I have not run this pipeline yet, so there is no trials table and no model B in this post. What we do have is the baseline the run has to beat: model A with the knowledge base, measured on the AWS Community Day cluster with `just eval`:

| Setup                                                           | Score |
| --------------------------------------------------------------- | ----- |
| Model A, whole knowledge base in the prompt                     | 6/15  |
| Model A, keyword retrieval (the prompt gets the matching lines) | 11/15 |

The misses are not random. Questions about one line work: where and when the event is, or which room a talk is in when you give its full title. Questions where the model has to scan many lines fail: "who speaks from AWS?" or "what is on the Main Stage after lunch?". A section that groups speakers by company turned the first one into a one-line lookup, and the model got it right 3 times out of 3.

That changes my guess from the start of this post. The biggest gap so far is how much context the 1.5B model gets, not its weights. Sending fewer, better lines (retrieval) gained more than any LoRA setting is likely to.

## What's Next

The pipeline in this post is ready to run, but it needs two changes first (see [What Fine-Tuning Could Teach](#what-fine-tuning-could-teach)):

1. A dataset built from the knowledge base, in place of `guanaco-llama2-1k`.
2. Loss masking, so training counts the answer and not the prompt.

Then one run answers three questions with the same test set: does LoRA beat base Qwen with the knowledge base, does tuning beat the old settings, and does either one beat retrieval. I will add the results here once that run happens.

## Conclusion

Ray Tune fits into the pipeline as one more step, without touching the RayCluster that serves users. Ray Tune runs in the training pod, ASHA stops the weak trials after one epoch, and the old settings run as one of the trials. When the old settings have the lowest loss, the pipeline skips the training and keeps model A.

The bigger lesson came before any tuning: measure the thing you want to improve. For our event chatbot, the numbers so far point at the prompt, not the weights. Tuning is ready for the day a dataset says the weights matter.
